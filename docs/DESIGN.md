## 1. 目的

麻雀大会のPC配信で、牌の自動読み取り・点数計算・ゲーム中継風の情報表示・映像切替までを行うシステムを作る。
**処理は2台に分ける**: カメラ映像を扱う重い処理はノートPC（処理サーバー）で行い、LANには処理済みのデータだけを流す。配信用の画面づくり・操作・配信は別PC（配信クライアント）で行う。

### 想定する使い方
1. ノートPCで **JanScope サーバー** を起動 → 手牌カメラ・盤面カメラを取り込み、牌認識と卓状態の管理を始める
2. 配信用PCで **JanScope クライアント** を起動し、サーバーに接続 → 「出力ウィンドウ（配信用）」「操作ウィンドウ」が開く
3. クライアントは受け取ったデータ（点数・手牌・河・副露など）を牌画像で描画し、顔カメラ（RTMP）などのメイン映像と合成して出力ウィンドウに表示
4. 配信用PCの OBS が出力ウィンドウをゲームキャプチャで取り込み、音声と合わせて配信する
5. 操作（対局入力・手修正・映像切替）はすべてクライアントから行い、サーバーに送る
6. 選手用画面と入力担当ウィンドウも配信用PCで動かし、それぞれ別モニターに表示する（4.8・4.11）

### 方針
- **LANに映像を流さない**。サーバー→クライアントは処理済みデータ（数KB程度のメッセージ）だけ。手修正に必要な牌の小さな切り抜き画像だけは、必要なときに送る
- 情報の描画はクライアントのGPUで行い、遅延を最小にする
- 音声は本ソフトでは扱わない。映像の遅延値を表示し、OBS側の音声同期オフセットに入れられるようにする
- 出力モードは2つ:
  - **合成モード（既定）**: 映像込みの完成画面（不透明）
  - **オーバーレイのみモード**: 映像なし、情報表示だけを透過で出力（OBS側で映像を合成したい場合用）
- デザイン（配色・ロゴ・装飾）は仮の簡素なもので進め、後で差し替える。テーマとして分離しておく
- **開発は「牌認識が使えるか」の検証から始める**（10章）。カメラの調達・接続テストは、検証結果でカメラの条件が決まってから行う

### やらないこと（初版）
- 音声の入出力・ミキシング
- 配信・録画そのもの（OBSが担当）
- LAN経由での映像の送受信（顔カメラのRTMPはクライアント側で直接受ける）
- 複数卓の同時中継（将来拡張として構造だけ考慮）
- 三人麻雀
- チーム戦

| 操作UI | `bevy_egui` | クライアントの操作ウィンドウ・入力担当ウィンドウ、サーバーの管理画面 |
| 通信 | WebSocket（`tokio-tungstenite` 等）＋ JSON（量が増えたら MessagePack） | サーバー⇔クライアント。LAN内のみ。ライブラリのライセンスは導入時に確認 |
| 構成 | Cargo ワークスペース（`core`: 卓状態・ルール・mahc・通信の型 ／ `server` ／ `client`） | 1つのリポジトリで管理。サーバーとクライアントは別の exe |
| フォント | SIL Open Font License の日本語フォント（例: Noto Sans JP）を同梱 | OFLの条件（フォント単体での販売禁止など）を THIRD_PARTY_LICENSES に記載 |

| 配布 | Windows向け zip（解凍してexe起動） | |

- 通信はLAN内のサーバー⇔クライアント間のみ（ほかは自動アップデートの取得だけ）

## 3. 全体構成

### 3.1 2台構成

```
┌─────────────── ノートPC：JanScope サーバー ───────────────┐
│ [手牌カメラ×4][盤面カメラ] ─USBハブ─▶ 映像入力                       │
│        ▼                                                    │
│   牌認識（GPU） → 卓状態の推論 → 卓状態管理（正）＋ mahc計算＋ログ保存   │
│        ▲                                    │               │
│   操作（Action）を受けて反映                   │ 処理済みデータ     │
│   管理画面（カメラ確認・校正・状態表示）         │               │
└─────────────────────────────────────────────┼───────────────┘
              LAN（データのみ。映像は流さない）   │ WebSocket
┌─────────────────────────────────────────────┼───────────────┐
│ 配信用PC：JanScope クライアント                 ▼               │
│   受信データ → 牌画像で描画（手牌・河・副露・点数…）＋ 配信ディレイ       │
│   顔カメラ（RTMP）を直接受信 → メイン映像の切替・合成                  │
│   → 出力ウィンドウ 1920×1080 → OBS ゲームキャプチャ → 配信           │
│   操作ウィンドウ（対局入力・映像切替）                               │
│   ＋ 入力担当ウィンドウ（手修正、別モニター）                          │
│   ＋ 選手用画面（別のプロセスとして起動、会場向けの別モニター）           │
│     ※選手用画面は公開情報だけを受け取る（サーバー側で手牌などを除いて送る）  │
└────────────────────────────────────────────────────────────┘
```

| 役割 | 置き場所 | 担当すること |
|---|---|---|
| サーバー | ノートPC | 手牌・盤面カメラの取り込み、牌認識、卓状態の推論と管理（正となる状態）、点数計算（mahc）、ログ保存、クライアントへの配信、カメラ確認・校正の管理画面 |
| 配信クライアント | 配信用PC | 情報の描画、配信ディレイ、顔カメラ（RTMP）の取り込みとメイン映像の切替・合成、出力ウィンドウ、操作ウィンドウ、OBSでの配信 |
| 入力担当クライアント | 配信用PCの別モニター | 手修正・要確認キュー・残り牌数・牌譜入力（4.11）。配信クライアントと同じexeを「入力担当モード」で起動 |
| 選手用画面クライアント | 配信用PCにつないだ別モニター（用意済み） | 公開情報だけの表示（4.8） |

- 正となる状態は**サーバーだけ**が持つ。クライアントは表示と操作の送信だけ。
- 状態は「操作（アクション）のログ」から再計算する方式（イベントソーシング）。Undo・やり直し・クラッシュ復元を単純にする。
- 出力ウィンドウは枠なし・サイズ固定。最小化すると描画が止まりキャプチャできなくなるため、最小化しない運用を注意表示する。

### 3.2 通信設計

- **方式**: サーバーが WebSocket で待ち受け、クライアントが接続する。LAN内のみ
- **接続**: サーバーのIPアドレスとポートを入力して接続（LAN内の自動検出は将来対応）。サーバー画面に表示する**接続コード**を入力しないと接続できない（会場の他の機器からの誤接続・のぞき見防止）
- **クライアントの種類（ロール）**: 配信 ／ 入力担当 ／ 選手用画面。**サーバーはロールごとに送る情報を絞る**。選手用画面ロールには手牌・未公開情報・認識データを一切送らない（4.8の情報漏れ防止をサーバー側で保証する）
- **送るもの（サーバー→クライアント）**:
  - 接続直後に卓状態の全体（スナップショット）、以後は変更点（イベント）を連番付きで送る
  - イベント: 点数・局・リーチ・ツモ・打牌・鳴き・ドラ・残り牌数・アガリ結果・要確認の発生 など。すべてサーバー時刻付き
  - 手修正用の牌の切り抜き画像（小さなJPEG）は、入力担当クライアントが要求したときだけ送る
- **送るもの（クライアント→サーバー）**: 操作（Action）、手修正、プレビュー要求（アガリの計算だけ）、切り抜き画像の要求
- **映像切替（VideoCommand）はクライアント内で完結**（サーバーには記録用に通知するだけ）
- **時刻合わせ**: 接続時と定期的に時刻差を測り、サーバー時刻で表示タイミング（配信ディレイ）を合わせる
- **切断・再接続**: クライアントは自動で再接続し、連番の抜けがあればスナップショットを取り直す。切断中も出力ウィンドウは最後の状態を表示し続け、操作ウィンドウに「切断中」と大きく表示
- **サーバーが落ちた場合**: 再起動時にログから状態を復元し、クライアントは自動で再接続
- **通信量の目安**: 1秒あたり数十件・数十KB以下（映像を流さないため、一般的な有線LANで十分。Wi-Fiも可だが有線推奨）

## 4. 画面設計

### 4.1 映像ソースの考え方

**ソース = 入力デバイス ＋ 切り出し範囲 ＋ 向き補正 ＋ 名前**

- 1台のデバイスから複数のソースを切り出せる（例: 卓の真上カメラ1台の映像から、4人分の手牌＋河を正方形で切り出す。ハードウェアのマルチビュー出力を1本のHDMIで受けて分割する、なども可）。カメラ台数が少なくても成り立つ
- 向き補正: 回転（90°単位、および任意角度）・左右反転・上下反転。4人の手元を同じ向き（各選手から見た向き）にそろえるため
- 色の簡易補正（明るさ・コントラスト・彩度）
- 信号なし時は代替画像（選手名入りの静止画、なければ「NO SIGNAL」）を表示

**役割への割り当て**
- 顔カメラ・手牌カメラは**席（物理的な席A〜D）に割り当てる**。選手は席に座らせる形で登録するので、半荘ごとに選手が入れ替わっても映像・認識結果は自動で正しい選手の枠に出る

| 役割 | 数 | 用途 |
|---|---|---|
| 顔カメラ | 4（席ごと） | 選手画面（左上の大枠）。1人ずつ切り替えて表示。**別の配信元から RTMP で取り込む**（4.11） |
| 手牌カメラ | 4（席ごと） | **隠れた手牌（選手の側を向いて立っている牌）専用のカメラ**を1人1台ずつ用意。選手の手牌の表面を撮り、牌の自動読み取り（4.10）に使う。**配信画面には映さない**（全画面映像シーンで使うことは可） |
| 盤面カメラ | 1 | 卓全体を真上から撮る（200万画素。打牌エリアだけが画面いっぱいに入るよう画角を詰める）。**河・副露・ドラ表示牌など、表向きの牌の自動読み取り用**（隠れた手牌はこのカメラでは読まない）。配信画面には映さない（全画面映像シーンで使うことは可） |
| 卓俯瞰 | 0〜1 | 全画面映像シーン用（任意） |
| 実況席 | 0〜1 | 全画面映像シーン用（任意） |
| 予備 | 任意 | 自由に使う |


- 表示: 映っている選手の自風・親マーク・選手名・リーチ表示（点数はスコア表で見せるので出さない。設定で表示も可）
- 切替時はカット／短いフェード（設定）

#### 局情報（右上の最上段、854×100）

- 表示: 場風＋局数（例「東2局」）、本場（例「1本場」）、供託（リーチ棒の本数または点数、設定で選択）
- オーラスは「オーラス」表示を追加（設定でON/OFF）
- 局が変わったときに短いアニメーション（設定でON/OFF）

#### スコア表（右上、854×300）

- 1行あたり: 自風・親マーク・選手名・所属（任意）・持ち点・順位・点差・リーチ表示
- 選手画面に映っている選手の行を強調（枠または背景色）
- 並び順: 席順固定（既定）／順位順（順位が変わると入れ替わりアニメーション）を設定で選択
- 点数移動の±表示は各行に出す

#### サイコロ（260×200）

- オペレーターが出目（2個、各1〜6）を入力して表示。サイコロの絵＋合計
- 局が始まるたびに入力。未入力の間は前局の出目を薄く表示するか非表示（設定）
- 2度振り（ルールによる）の場合は2回分を並べて表示（設定でON/OFF）

#### ドラ表示牌（334×200）

- ドラ表示牌を牌画像で表示。槓ドラ追加で枚数が増える
- 設定で「表示牌」／「実際のドラ牌」／「両方」を選択（既定: 表示牌）

#### 残り牌数（260×200）

- 山の残り枚数（ツモれる残り）を大きな数字で表示
- 局開始時に初期値（既定70、ルール設定で変更可）にリセット
- **入力方法**: 1回のツモごとに減らす必要があるため、オペレーター負担を減らす工夫をする
  - 専用キー1つ（既定: テンキーの「-」、変更可）を押すたびに1減る。押し間違い用に「+」で1戻す
  - 槓が入ったら1減らす（嶺上牌の補充で海底がずれるため）。槓の入力時に自動で処理
  - 数値の直接修正もできる
  - 外付けのキーパッド・フットスイッチ（キーボードとして認識されるもの）でも押せるようにする
- 残り数が少なくなったら（既定: 残り4以下）強調表示

#### 手元枠（下段、480×480 ×4）

**カメラ映像ではなく、牌認識（4.10）の結果を牌画像で描き直して表示する。**
カメラ → 牌認識 → 卓状態データ（手牌・河・副露） → 牌画像で再配置、という流れ。

```
 ┌──────────────────────────┐
 │ 東[親] 選手名  [リーチ]     │ ← 上部の帯（約40px）
 │                          │
 │   河（6枚ずつ折り返し）      │
 │   ■■■■■■                │
 │   ■■■■■■                │
 │   ■■■□(横向き=リーチ宣言牌)   │
 │                          │
 │ ■■■■■■■■■■ ■  [副露]     │ ← 手牌（理牌して表示）＋ツモ牌（少し離す）＋副露（右端）
 └──────────────────────────┘
```

- 河: 6枚ずつ折り返し、最大4段（それ以上は縮小）。リーチ宣言牌は横向き、鳴かれた牌は暗く表示
- 手牌: 理牌（萬・筒・索・字の順に並べ替え）して表示。ツモ牌は少し離して右に置く。副露があるときは手牌の牌を縮小して右端に副露を並べる（横向き牌も再現）
- 牌の並べ方は牌譜再生（4.9）と同じ描画部品を共用する
- **表示するのは確定した認識結果だけ**。要確認（確信度が低い・矛盾がある）の牌は、手修正が終わるまで直前の確定状態を表示する
- 自動読み取りが止まっている・OFFのとき: 帯に「手動」と小さく出し、手入力された内容（なければ空の枠）を表示
- 席A〜Dの順に左から並べる（並び順は設定で変更可）
- 上部の帯: 自風・親マーク・選手名・リーチ表示
- 選手画面に映っている選手の枠を強調（枠線）
- リーチ中は枠の色を変える（設定）

#### アガリ演出
- 上段（選手画面＋局情報＋スコア表＋サイコロ等の領域、1920×600）に重ねて表示: アガった選手名・手牌（牌画像で描画）・役一覧・翻符・点数
- 同時にアガった選手の手元枠を強調（手牌を倒した状態の表示に切替）、選手画面をアガった選手に切替
- 演出終了後、点数移動の±表示 → 通常表示に戻る

#### テロップ
- 任意の文字を表示（位置は設定。既定はスコア表の下端に重ねる）

### 4.7 選手画面の切替

選手画面（左上の顔映像）に映す選手を、自動または手動で切り替える。

**モード**
| モード | 動作 |
|---|---|
| 自動 | 下の優先順位に従って自動で切り替える（既定） |
| 一時手動 | 手動で選んだ選手を表示し、設定秒数（既定30秒）後に自動へ戻る |
| 手動固定 | 手動で選んだ選手を、「自動」を押すまで表示し続ける |

手動で選んだときに「一時手動」と「手動固定」のどちらになるかは設定で選ぶ（既定: 一時手動）。

**自動切替の優先順位（上ほど優先。各項目のON/OFF・順番・表示秒数は設定で変更可）**
1. アガリ演出中 → アガった選手（ダブロンは演出の順に切替）
2. 放銃直後 → 放銃した選手（既定OFF）
3. リーチ宣言 → リーチした選手（既定10秒）
4. 槓 → 槓をした選手（既定OFF、5秒）
5. 上記に該当しない間 → 巡回（席順に一定間隔で切替、既定15秒）。巡回の代わりに「親を表示」も選択可

**切替の制御**
- 最短表示時間（既定5秒）: 切替直後は、より優先度の高いきっかけ（アガリ等）以外では切り替えない。画面がチカチカしないため
- 同時にきっかけが重なった場合は優先順位の高いほうを採用
- 顔カメラが信号なしの選手は自動切替の対象から外す

### 4.8 選手用画面（会場の選手向けモニター）

対局中の選手が見るための画面。**配信用PCで選手用画面ロールのクライアントを別プロセスとして起動し、会場向けの別モニター（用意済み）に全画面表示する。** 配信用・入力担当とは別の接続にすることで、サーバー側の情報の絞り込みが確実に効く。**河・手牌・顔は不要なので、配信用レイアウトの流用ではなく、選手用の専用レイアウト・専用の描画系統として作る**。

**最重要: 選手に見せてはいけない情報を絶対に出さない**
- 河・手牌・顔は表示しない（映像・牌画像のどちらでも）。カメラ映像は一切使わない
- 裏ドラ・アガリ前の手牌など、卓上で公開されていない情報を出さない
- **サーバー側で、選手用画面ロールには公開情報だけを送る**（手牌・認識データ・裏ドラ・アガリ前の情報は送信自体しない）。クライアント側の設定ミスがあっても漏れない
- クライアント側でも「表示してよい部品の一覧（ホワイトリスト）」から組み立て、配信用レイアウトの設定変更の影響を受けない別系統にする

**表示する内容**
- 局情報（場風・局数・本場・供託）
- 4人の持ち点・順位・点差・リーチ表示・親マーク
- ドラ表示牌、残り牌数、サイコロの出目
- アガリ確定後の結果（役・翻符・点数・点数移動）。手牌は表示しない

**レイアウト（1920×1080、既定）**

```
 ┌──────────────────────────────────────────────────┐
 │        東2局   1本場   供託 1000                     │ 局情報（大きく）
 ├──────────────────────────────────────────────────┤
 │                     北 選手D                        │
 │                     22,000                         │
 │   西 選手C        ┌─────────────┐      南 選手B      │
 │   21,000         │ ドラ [牌][牌] │      25,000       │
 │                  │ 残り 42      │                   │
 │                  │ サイコロ ⚂⚄  │                   │
 │                  └─────────────┘                   │
 │                     東[親] 選手A                     │
 │                     32,000                         │
 └──────────────────────────────────────────────────┘
```

- 卓の配置どおりに4人を上下左右に置く（卓配置）。モニターが置かれる向きに合わせて、どの席を下にするかを設定で回転できる
- 一覧表示（縦に4行）にも切り替え可能
- 遠くからでも読めるよう、文字は配信用より大きく（既定）
- 点差表示のON/OFF（大会ルールで他家の点数を見せない場合に対応して、他家の点数自体を隠す設定も用意）

**出力**
- 表示するモニターを設定で選択し、全画面表示（枠なし）
- 解像度は接続モニターに合わせる（1920×1080基準で拡大縮小）
- 選手用画面をOFFにすることもできる
- 配信用出力とは描画のみ別で、状態は同じもの（同時に更新される）

### 4.9 牌譜再生（麻雀ゲーム風）

普通の麻雀ゲームのような卓画面（4人の手牌・河・鳴き・ドラ・点数）を描画し、牌譜を1手ずつ再生する。

**前提: 牌譜の入手方法**
本ソフトの通常の対局入力（点数・アガリ・リーチ等）だけでは、ツモ・打牌の1手ずつの記録は残らない。そのため牌譜は次のいずれかで用意する。
0. **自動読み取り（4.10）で生成した牌譜**: 対局中に自動で記録され、手修正済みのものを再生できる
1. **牌譜ファイルの読み込み（初版で対応）**: 天鳳形式のJSON牌譜（各種AI解析ツールで共通に使われている形式）を読み込む。将来、MJAI形式・電脳麻将形式にも対応
2. **牌譜入力モード（第2版で対応）**: 対局後に録画を見ながら、ツモ・打牌・鳴きを牌パレットとショートカットで入力する専用画面。入力した牌譜は天鳳形式JSONで書き出せる（AI解析ツールにそのまま渡せる）
3. 対局中に手ですべて入力するのは負担が大きすぎるため対象外（自動読み取り＋手修正で対応する）

**表示（1920×1080、出力ウィンドウの「牌譜再生」シーン）**

```
 ┌──────────────────────────────────────────────────┐
 │                北: 手牌（13枚）                    │
 │                北: 河                              │
 │  西:  ┌──────────────────────────┐   南:      │
 │  手牌 │  東2局 1本場 供託1  残り42        │   手牌 │
 │  ＋河 │  ドラ表示牌 [牌]                  │   ＋河 │
 │       │  各家の点数・風・リーチ棒          │        │
 │       └──────────────────────────┘        │
 │                東: 河                              │
 │                東: 手牌（13枚）＋ツモ牌             │
 └──────────────────────────────────────────────────┘
```

- 一般的な麻雀ゲームと同じ卓配置: 自分（視点の選手）が下、対面が上、上家が左、下家が右。河は6枚ずつ折り返し、リーチ宣言牌は横向き、鳴いた牌は河で暗く表示、副露は手牌の右に横向き牌を含めて表示
- 手牌の表示: 全員オープン（既定）／視点の選手だけオープン、を切替
- 視点の切替: 東南西北どの選手を下にするか
- 再生中のアクション表示: 「リーチ」「ポン」「チー」「カン」「ロン」「ツモ」を大きく表示
- アガリ時: 4.2 と同じアガリ演出（役・翻符・点数）、裏ドラもめくる
- 牌画像は 7章の素材を使用。デザインは特定の市販ゲームの見た目を模倣しない（配置は麻雀の一般的な形式に従い、装飾はテーマで独自に作る）

**操作（操作ウィンドウの「牌譜再生」パネル）**
- 牌譜ファイルを開く、局の一覧から選ぶ
- 再生／一時停止、1手進む／戻る、局の先頭へ／次の局へ、任意の巡目へジャンプ（スライダー）
- 再生速度（0.5〜4倍）
- 視点・手牌公開の切替
- 「名場面」として局と開始巡目をブックマークし、すぐ呼び出せる
- ショートカット対応（←→で1手、Spaceで再生／停止など）

**安全**
- 牌譜再生は**選手用画面には絶対に出さない**（手牌が見えるため）。選手用画面の描画系統から牌譜再生の部品を参照できない構造にする
- 対局中に配信側で牌譜再生シーンを出す場合、再生できるのは「終了した局」の牌譜だけにする（進行中の局の情報を流さない）

### 4.10 牌の自動読み取り（手牌カメラ4台＋盤面カメラ1台）

カメラ映像から牌を認識し、手牌・ツモ・打牌・鳴き・ドラ表示牌を自動で追跡する。**読み取り結果はいつでも手で修正でき、修正が常に優先される。**

#### カメラの分担
- **手牌カメラ（4台、1人1台）**: 隠れた手牌専用。選手の手牌の表面を正面〜斜め上から撮る。ツモ牌（手牌に加わる14枚目）もこのカメラで読む
- **盤面カメラ（1台）**: 表向きの牌（河・副露・ドラ表示牌・槓で開いた牌）を真上から読む
- 打牌は「手牌カメラで手牌から1枚減った」＋「盤面カメラで河に1枚増えた」の両方で突き合わせて確定する（片方だけの場合は確信度を下げる）

#### 何が自動化されるか
| 項目 | 自動化の内容 |
|---|---|
| 牌譜 | ツモ・打牌・鳴き・リーチ（横向きの宣言牌）を記録し、牌譜を自動生成（4.9 で再生、天鳳JSONで書き出し） |
| 残り牌数 | ツモ・槓から自動計算（専用キーでの手動操作は予備として残す） |
| ドラ表示牌 | 盤面カメラから自動で読み取り |
| アガリ入力 | アガった選手の手牌・副露・アガリ牌・ドラ・裏ドラを自動で埋めた状態で 4.5 の入力画面を開く。オペレーターは確認・修正してプレビュー → 放送 |
| リーチ | 河の横向き牌から検出し、リーチ表示の候補を出す |

#### 処理の流れ
```
[手牌カメラ×4] [盤面カメラ]
      │ 認識用は表示用とは別に、高解像度のままフレームを取得
      ▼
[領域の切り出し＋射影補正]  ← 事前の校正（4隅クリック）で、手牌・河・副露・ドラの領域を定義
      ▼
[牌の検出・分類（ONNXモデル、GPU）]  → 牌ごとの種類・位置・向き・確信度
      ▼
[時間方向の安定化]  ← 既定3フレーム（10fpsで約0.3秒）連続で同じ結果になったら確定（手の映り込み・ブレを除外）
      ▼
[卓状態の推論]  ← 前回との差分からイベントを推定（ツモ・打牌・ポン等）。麻雀のルールで矛盾チェック
      │          （同じ牌は4枚まで、手牌は13/14枚、河は打牌順に1枚ずつ増える、など）
      ▼
[イベント候補] ─(確信度 高)─▶ 自動確定（設定で「承認制」にもできる）
      └─(確信度 低・矛盾あり)─▶ 操作ウィンドウで要確認として表示
```

#### 技術
| 項目 | 内容 |
|---|---|
| 推論 | ONNX Runtime（Rust の `ort` crate）、描画（Bevy）とは別スレッド。GPU実行の方式（DirectML 等）は、同梱が必要になる実行ファイルのライセンスがAGPL-3.0と両立するかを段階A2で確認して決める。両立しない場合は Windows 標準搭載のものだけを使うか、CPU実行で精度・速度を測る |
| モデル（2段構成） | **① 検出: Ultralytics YOLO**（https://github.com/ultralytics/ultralytics 、AGPL-3.0）で牌の位置だけを1クラス「牌」として検出（必要なら手牌・河・副露・ドラの領域検出も追加）。学習・ONNX書き出しの手順が整っていて扱いやすい。**代替: RF-DETR**（Apache-2.0。使う場合は Apache-2.0 のサイズのみ）。② 射影補正で牌1枚を正面向き・一定サイズ（例: 96×128）に切り出し。③ **分類: 小型CNN**（ResNet18 / MobileNet 等。ライセンスがBSD・Apache等のものを使用）で 34種＋赤5＋裏向き を判定。小さく写った牌でも、分類段で拡大して判定できるため200万画素に向く |
| 公開モデルの扱い | **既存の学習済み牌認識モデルは使わない。自前で学習する。** Hugging Face の HaseLab/mahjong-models は構成（領域検出→牌検出→射影補正→ResNet-50分類）の考え方だけ参考にし、重み・コードは試用も含めて使わない（ライセンス表記がないため）。学習したモデルの重みはAGPL-3.0として公開する |
| モデル出力 | 学習後 ONNX に書き出し、Rust 側は `ort` で読む |
| 学習 | 学習用スクリプトは Python で別ディレクトリ（`training/`）に置く。配布物には含めない |
| 学習データ | **大会で実際に使う牌セットで撮影した画像を基本にする**（牌のデザイン・色は牌セットごとに違うため）。7章の牌画像から合成したデータを補助に使う。公開データセット（Roboflow Universe 等）は、**AGPL-3.0と両立するライセンスが明記されているものだけ**を事前学習の補助に使う。表記がない・不明なものは使わない |
| 注釈付けツール | Label Studio または CVAT（どちらもオープンソース。導入時にライセンスを確認）。学習データ収集（段階A1・C2）から書き出した画像に枠と牌名を付ける |
| 処理頻度 | 入力と同じ 10fps で全フレームを認識（描画の60fpsとは独立）。5台×10fps＝毎秒50枚の推論。GPU負荷を見て間引きも可能 |

#### 校正（大会前の準備）
- カメラごとに、手牌・河（4人分）・副露・ドラ表示牌の領域を、プレビュー上で4隅をクリックして指定（射影補正）
- 照明・カメラ位置を固定した状態で、テスト用の牌を並べて認識精度を確認する「認識テスト」画面
- 校正データは卓・会場ごとにプリセット保存

#### 手修正（随時）
- **ライブ確認ビュー**: 各カメラ映像に、認識した牌の枠と牌名を重ねて表示。確信度が低い牌は色を変える。**カメラ映像はサーバー（ノートPC）の管理画面でだけ見る**（LANに映像を流さないため）。入力担当クライアントには、要確認の牌の小さな切り抜き画像と、必要時のみ低解像度・低頻度の静止画を送る
- **卓状態ビュー**: 認識結果から作った現在の卓（4人の手牌・河・副露・ドラ）を、牌譜再生と同じゲーム風の画面で表示
- 修正方法:
  - 牌をクリック → 牌パレットで正しい牌に変更
  - 牌の追加・削除・並べ替え（ドラッグ）
  - イベント一覧（時系列）から、誤ったイベント（例: 打牌の牌違い、ポンの見逃し）を修正・挿入・削除
  - 「この局面で認識を一時停止」→ 手で直してから再開
- 修正は手動入力として記録し、以後の推論は修正後の状態を前提に続ける（修正が常に優先）
- 修正した画像と正解は「学習データ候補」として保存し、後でモデルの再学習に使える（保存はON/OFF可）
- **要確認キュー**: 確信度の低い認識・矛盾のある推論を一覧で出し、オペレーターが1件ずつ承認／修正する。ショートカットで素早く処理できる

#### 動作モード（設定で選択）
| モード | 内容 |
|---|---|
| 自動確定（既定） | 確信度が高いものは自動で確定。低いものだけ要確認 |
| 承認制 | すべてのイベントをオペレーターが承認してから確定 |
| 記録のみ | 認識はするが、残り牌数・ドラ等の表示には使わない（牌譜作成用に裏で記録するだけ） |
| OFF | 自動読み取りを使わない（従来の手入力のみ） |

#### 安全・運用
- 認識した手牌の情報は**選手用画面には絶対に出さない**（4.8 の構造的な分離を維持）
- 手牌情報はLAN内のサーバーと配信・入力担当クライアントの間だけで扱い、インターネットには送信しない。選手用画面ロールには送らない
- 配信に手牌が映るので、必要に応じて配信ディレイをかける。ディレイは本ソフトの設定で変更できる（4.11）
- 認識が止まっても、従来の手入力（4.4）で大会を続行できること（認識は補助であり、なくても成り立つ）

### 4.11 顔カメラのRTMP取り込み・配信ディレイ・入力担当ウィンドウ

#### 顔カメラ（RTMP）
- 顔カメラは別の配信元（別PC・配信機材など）から RTMP で送られてくる映像を取り込む。取り込みURLを設定で登録
- 本ソフトが RTMP を受ける方式（本ソフトがサーバーとして待ち受ける）と、配信元のサーバーから引っ張る方式の両方に対応できる設計にする（実装時にどちらから作るか確認）
- RTMP は数秒の遅延が出やすい。ソースごとの「同期補正（ms）」で、牌の表示（データ）や他の映像とタイミングを合わせられるようにする
- **取り込めない場合の代替（最悪の場合）**: 選手画面を黒（またはクロマキー色）の枠にして、OBS側で顔映像を重ねる。この場合も
  - 選手名・自風・リーチ表示の帯は本ソフトが描画する
  - 選手画面の自動／手動切替（4.7）の結果は、OBS の obs-websocket（OBS標準の操作機能）経由で OBS のシーンまたはソースの表示を切り替えて反映する（設定でON/OFF、接続先とソース名を設定）。使わない場合は OBS 側で手動切替
- RTMP が途切れたら代替画像に切り替え、復帰したら自動で戻す

#### 配信ディレイ（設定で変更）
- 出力ウィンドウ全体を、設定した秒数だけ遅らせて表示する（既定0秒）。ちゃんとした大会以外でも気軽に使えるよう、操作ウィンドウからいつでも変更できる
- 実現方法:
  - **データ**（点数・手牌・河・演出など）: 卓状態の変化を時刻付きで記録し、「今 − ディレイ秒」の状態を描画する（軽い）
  - **映像**（顔カメラなど）: デコード前の圧縮データ（MJPEG・H.264）を時刻付きでリングバッファに溜め、ディレイ秒後にデコードして描画する（メモリが少なくて済む）
  - バッファ上限（例: 10分）とメモリ使用量の目安を設定画面に表示
- ディレイ中も、操作ウィンドウ・入力担当ウィンドウは常にライブ（遅延なし）。プレビュー→放送の確認もライブで行う
- ディレイ秒数を変えた瞬間は映像が飛ぶため、確認ダイアログを出す（または次のシーン切替時に反映）
- 選手用画面（4.8）はディレイの対象外（選手はリアルタイムで見る必要がある）。手牌を出さないので問題ない
- OBS 側の配信遅延機能を使う運用も可（その場合は本ソフトのディレイを0にする）

#### 入力担当ウィンドウ（専任）
- 自動読み取りの手修正・要確認キューの処理・残り牌数・牌譜入力は**専任の入力担当**が行う
- 配信用PCで「入力担当」ロールのクライアントを起動し、別モニターに表示する。サーバーに接続し、同じ状態を共有する
- 入力担当ウィンドウの内容: 要確認の牌の切り抜き画像＋認識結果、卓状態ビュー、要確認キュー、牌パレット、イベント一覧の修正、残り牌数の操作、アガリ入力の下書き
- メインの操作ウィンドウ側には、入力担当が修正中であること・要確認の件数を小さく表示する
- 同じ項目を2人が同時に操作した場合は、後の操作を優先し、相手側に通知する

## 5. 機能要件

### 5.1 卓状態
- 4人の持ち点、局（場風・局数）、親、本場、供託、リーチ状態
- サイコロの出目、ドラ表示牌、残り牌数
- 局の自動進行（親流れ・連荘・南入・オーラス判定・終局判定）
- 終局条件はルール設定に従う（箱下終了、西入など）

### 5.2 点数計算
- アガリ: mahc で翻・符・役・点数を取得し、ツモ/ロン・親子・本場・供託を反映して点数移動を作る
- 流局: ノーテン罰符（場3000）、流し満貫（手動指定）。残り牌数が0になったら流局入力を促す
- 途中流局: 九種九牌・四風連打・四開槓・四家立直・三家和（ルール次第）
- 手動調整: チョンボ、包（パオ）、その他の点数修正（理由を入力してログに残す）

### 5.3 大会ルール設定（プリセット＋編集、編集は 4.6 のルールタブで行う）
- 持ち点・返し、ウマ、オカ
- 赤ドラ枚数、喰いタン、後付け
- 東風/東南、西入の有無、箱下終了
- ダブロン・トリロンの扱い（頭ハネ／全員）
- 切り上げ満貫、数え役満、ダブル役満の有無
- 本場の点数（300点）
- 連風牌の雀頭の符（2符/4符）
- 途中流局の有無（種類ごと）
- 同点時の順位の決め方（起家優先など）
- 局開始時の残り牌数の初期値（既定70）、サイコロの2度振りの有無
- ルールはJSONファイルで保存・読込（保存形式のみ。編集はUIから）
- 一般的な競技ルールのプリセットを数種類同梱（あくまで初期値。大会側で編集して使う）

### 5.4 日本語表示
- mahc の役名・符内訳（英語）を日本語に変換する対応表を用意（`src/i18n/yaku_ja.rs` 等）
- 未対応の役名が来たらそのまま表示し、ログに警告

### 5.5 Undo・保存・復元
- すべての対局操作をアクションとしてログに追記（JSON Lines）。残り牌数の増減もアクション
- 状態はログを先頭から再生して作る
- 起動時、前回のログがあれば「続きから再開」を選べる
- 半荘ごとにログファイルを分け、大会通算はそれを集計
- 映像の切替操作はログに残すが、Undoの対象にはしない（Undoは対局の操作のみ）

### 5.6 大会通算（個人戦）
- 半荘結果（最終ポイント）を蓄積し、選手別の通算順位を出す
- CSV出力（大会運営用）

### 5.7 映像
- 入力: 最大12ソース程度を想定（デバイスの本数はPC性能次第。切り出しでソース数を増やせる）
- **入力の基準: 200万画素（1920×1080）・10fps**（未検証。段階A3で解析に使えるか検証し、段階C1で実機確認する）
  - 利点: 9ソースでもUSB帯域・デコード・GPU負荷が軽い。認識も10fpsで全フレーム処理できる
  - ソースごとに解像度・fpsを設定で変更できるようにする（検証結果に応じて上げられるように）
- **10fpsの注意点（検証で確認する）**
  - 配信画面に映るカメラ映像は顔カメラ（RTMP、配信元の設定に従う）だけなので、手牌・盤面カメラの10fpsは配信の見た目に影響しない（手元枠は牌画像で描画するため）
  - 1フレームが100msなので、映像の遅延が最大100ms増える。OBSの音声同期オフセットで調整する（遅延値は 4.4 の状態表示に出る）
  - 打牌の動きが速いとブレやすい。照明を明るくしてシャッター速度を速く（1/250秒以上を目安）設定できるカメラが望ましい
- **200万画素での牌の大きさ（盤面カメラ）**
  - 打牌エリア約80cmを1080画素に収めると約13画素/cm、河の牌1枚が約25×35画素になる見込み。認識できる下限付近なので、段階A3で精度を必ず計測する
  - 足りない場合の対策: 画角を打牌エリアだけに詰める → 盤面カメラを2台に分ける（対角2人分ずつ）→ 盤面カメラだけ4Kにする、の順で検討
- 手牌カメラは手牌だけを大きく映せるので、200万画素で十分な見込み
- 手牌カメラ・盤面カメラは認識専用で配信には映さないため、画質より「牌がはっきり読めること」（ピント・照明・ブレ）を優先して設定する
- 入力が途切れても出力は止めない（代替画像に切替、復帰したら自動で戻す）
- デバイスの抜き差しを検知して再接続を試みる

### 5.8 機材の前提

**処理サーバー（ノートPC）**: Core i7-13700H、GeForce RTX 3060 Laptop（VRAM 6GB）、メモリ32GB

| 処理 | 見込み |
|---|---|
| 牌認識（検出＋分類、5台×10fps） | 小型モデル（YOLOの最小〜小サイズ＋小型CNN）なら余裕がある見込み。実測は10章の検証で行う |
| 映像のデコード（5台、MJPEG） | 軽い |
| 管理画面の描画 | 軽い（配信用の描画はクライアント側なので、サーバーの負荷は認識に集中できる） |

ノートPCの注意点:
- 必ずACアダプタを接続し、電源設定を「最適なパフォーマンス」にする。長時間で熱による性能低下が起きないか確認
- 認識を確実に RTX 3060 で動かすよう、Windowsのグラフィック設定でサーバーを「高パフォーマンス」に指定する（手順を README に記載）

**配信クライアント（配信用PC）**: Core i9-14900K、メモリ64GB、GeForce GTX 1660 Ti（VRAM 6GB）

| 処理 | 見込み |
|---|---|
| 描画（2D、60fps。出力・操作・入力担当・選手用画面の4ウィンドウ） | 余裕あり |
| 顔カメラ RTMP 4本のデコード | GPUのハードウェアデコード（NVDEC）で軽い。CPUでも余裕がある |
| OBS の配信エンコード | GTX 1660 Ti のハードウェアエンコーダ（NVENC）を使う |
| 配信ディレイのバッファ | 64GBで十分 |

配信用PCの注意点:
- **モニター出力**: 操作ウィンドウ・入力担当ウィンドウ・選手用画面で3画面（出力ウィンドウはOBSで取り込むので、操作画面の裏に置いてもよい。最小化は不可）。GTX 1660 Ti の出力端子で足りない場合は、CPU内蔵GPUの端子（マザーボード側）も使える。描画の重い出力ウィンドウはGTX 1660 Ti側のモニターに置く
- **Core i9-14900K の安定性**: 第13・14世代の上位CPUには長時間使用で不安定になる問題が知られており、Intel から対策済みのマイクロコードが出ている。大会前にマザーボードのBIOSを最新にしておく（8時間の通し試験の前提）

**LAN**: サーバーとクライアントは有線LANで接続を推奨（データだけなので帯域はわずか。安定性のため）

**カメラ接続（手牌カメラ4台＋盤面カメラ1台、USBハブ）※調達・テストは後回し**
- 1台のハブに複数のUSBカメラをつなぐと、帯域不足で一部のカメラが映らないことがある（UVCカメラは使う帯域を先に確保するため）。次の対策をとる:
  - カメラの出力形式は **MJPEG** を使う（非圧縮のYUY2は1080p・10fpsでも1台あたりの帯域が大きく、複数台は困難）。本ソフトは MJPEG を優先して選ぶ
  - **外部電源付き**の **USB 3.x ハブ**を使う。可能なら複数のハブに分け、PC本体の別々のUSBポートにつなぐ
  - カメラごとに「実際に届いているfps」を状態表示に出し、取りこぼしをすぐ気づけるようにする
- カメラの条件（解像度・画角・ピント）は、10章の段階Aの検証結果で決めてから調達する

## 8. 品質・テスト

- **点数計算の検証**: Python の `mahjong` ライブラリ（天鳳の大量牌譜で検証済み）と同じ手を両方で計算し、結果を突き合わせるテストを用意する（開発時のみ使用、配布物には含めない）。数百手以上のテストケースで一致を確認
- 卓進行の単体テスト（連荘・親流れ・終局・ダブロン・供託の行方・残り牌数と槓）
- 選手画面の自動切替の単体テスト（優先順位・最短表示時間・手動モード）
- **自動読み取りの精度評価**: 正解付きの評価用動画（大会の牌セット・照明で撮影）を用意し、牌1枚単位の認識率とイベント単位の正解率を計測する。目標値は段階A3の計測結果を見て決める
- 自動読み取りの回帰テスト: 評価用動画を流して、推論結果（牌譜）が正解と一致するかを自動で比較
- 認識停止・カメラ断のときに、手入力だけで大会を続行できること
- **牌譜の検証**: 実在の天鳳牌譜を多数読み込み、再生後の点数・アガリ点がファイル記載の値と一致すること（mahcでの再計算とも照合）
- **選手用画面の情報漏れテスト**: どの設定・どのタイミング（アガリ入力中のプレビュー、裏ドラ入力中、牌譜再生中など）でも、選手用画面にカメラ映像・未公開情報が出ないことを確認する自動テスト
- 異常系: 不正な手牌入力、アガリ形でない手 → エラー表示し、放送には出さない
- 映像: 入力の抜き差し、信号断、解像度違いの混在で出力が止まらないこと
- 長時間試験: 8時間連続稼働でメモリ増加・フレーム落ちがないこと（大会1日分）
- 負荷: サーバーで5台（200万画素・10fps）の認識10fpsを維持できること。クライアントで出力60fpsをOBS配信と同時に維持できること
- 通信: 切断・再接続・サーバー再起動で状態が正しく復元されること。選手用画面ロールに手牌などの情報が一切届かないこと（通信内容を記録して自動テスト）
- 遅延測定: カメラ入力から出力ウィンドウ表示までの遅延を計測・表示する機能を用意

## 10. 開発ステップ

カメラの調達・接続テストは後回し。**最初に「特定の解像度の映像で牌認識ができるか」を検証**し、その結果でカメラの条件を決める。

### 段階A：牌認識の実現性検証（カメラ不要）

| 段階 | 内容 | 完了条件 |
|---|---|---|
| A1 | 検証用の画像・動画を用意する。**実際に使うカメラを1台だけ先に用意**し、手牌カメラの位置・盤面カメラの位置の両方を想定して、牌を並べた写真・打牌の動画を撮る（設置距離・角度・照明を変えて複数パターン。牌セットは手持ちのものでよい。大会の牌セットの特定は後回し） | 手牌・河・副露・ドラの状態を含む画像が揃う |
| A2 | 注釈付け（牌の枠と種類）と、学習・評価用の Python スクリプト（`training/`、Ultralytics YOLO＋小型CNN） | 注釈付きデータで学習・評価が回る |
| A3 | **解像度ごとの精度評価**: A1のカメラの最大解像度で撮った画像を縮小して、「牌1枚が何画素あれば読めるか」「200万画素で河まで読めるか」を測る評価ツール（CLI。画像・動画ファイルを入力、精度表を出力） | 牌1枚あたりの必要画素数と、解像度・画角ごとの精度表ができる |
| A4 | 結果から、そのカメラで足りるか、残り4台も同じカメラでよいか、盤面カメラだけ別にするかを決める（解像度・画角・設置距離・fps） | 残りのカメラの調達条件が決まる |

### 段階B：本体（手入力で動く版）

| 段階 | 内容 | 完了条件 |
|---|---|---|
| B1 | Cargo ワークスペース（core／server／client）、卓状態・アクションログ・Undo、サーバー⇔クライアント通信（接続コード・ロール・スナップショット＋イベント・再接続） | クライアントから点数を手動変更 → サーバー経由で出力ウィンドウに即反映 |
| B2 | クライアントの出力ウィンドウ、OBSゲームキャプチャで取り込み、対局画面レイアウト（選手画面・局情報・スコア表・サイコロ・ドラ・残り牌数・手元枠） | OBSで遅延少なく取り込める |

- 選手用画面: 会場モニター向けの専用レイアウト（局情報・点数・ドラ・残り牌数・サイコロ・アガリ結果のみ。河・手牌・顔は出さない）
- 牌の自動読み取り: 手牌カメラ4台（隠れた手牌専用、1人1台）＋盤面カメラ1台。読み取り結果は随時手修正でき、修正が優先。認識は補助で、止まっても手入力で続行できる
- 牌認識モデル: Ultralytics YOLO（検出）＋小型CNN（分類）を自前で学習。既存の学習済みモデルは使わない
- 入力ソースの基準: 200万画素・10fps（ソースごとに変更可）
- 牌譜再生: 麻雀ゲーム風の卓画面で再生。天鳳JSONの読み込み、自動読み取りで作った牌譜、第2版で牌譜入力モード。選手用画面には出さない
- 個人戦のみ（チーム機能なし）
- 映像の入出力・合成は本ソフトで行い、OBSは取り込み・配信・音声を担当
- 全ソース公開（GitHub公開リポジトリ、既存のリポジトリを使う）、ライセンスは AGPL-3.0
- ソフト名: 仮称 JanScope
- 2台構成: ノートPC（Core i7-13700H／RTX 3060 Laptop／メモリ32GB）が処理サーバー、別PCが配信クライアント（操作・入力・メイン映像の制御・描画・配信）。LANには処理済みデータだけを流す
- 選手用画面・入力担当: どちらも配信用PCの別モニターで表示
- 配信用PC: Core i9-14900K／メモリ64GB／GTX 1660 Ti
- 段階A1: 実際に使うカメラを1台だけ先に用意して撮影
- 開発順: 牌認識の実現性検証（段階A）→ 手入力で動く本体（段階B）→ カメラ導入と自動読み取り（段階C）。カメラ調達は段階Aの後
- 手牌カメラ・盤面カメラ: 基本はUSBハブで接続
- 下段の手元枠: 牌認識の結果を牌画像で再配置して表示（手牌・河・副露）。カメラ映像は映さない
- 顔カメラ: 別ソースの RTMP 配信から取り込む。不可なら黒枠にして OBS で重ねる
- 配信ディレイ: 本ソフトの設定で秒数を変更できる（既定0秒）
- 手入力・手修正: 専任の入力担当が、入力担当ウィンドウで行う
